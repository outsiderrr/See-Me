# See Me — MVP 技术设计

> 状态:设计已与用户确认,待最终评审
> 日期:2026-06-21
> 产品 brief 见对话原文。本文是把 brief 翻译成的工程设计。

## 0. 核心假设(产品成败全看它)

人愿不愿意把「想被了解」从"推送给别人、索取反馈"换成"放在那里、等人主动来看、不要任何回应"。MVP 的唯一目的是验证它,不追求功能完整。

一句话定位:一个**没有压力的、可分组授权的朋友圈**。A 把想被了解的那部分自己写进个人文本库,用标签控制谁能看哪些内容;B 在自己好奇时主动来看——不推送、不通知、无点赞评论、读者无回应义务。

## 1. 技术栈与部署

- **Next.js 全栈**(React + 服务端,单一 TypeScript 代码库,前后端一体)。SSR 帮助国内首屏速度。
- **PostgreSQL**(权限模型是多对多关系,关系型最稳)。
- **Docker Compose** 一键起(app + postgres);**Nginx** 反代 + **Let's Encrypt** HTTPS。
- 自托管在用户的**东京阿里云 ECS(8G)**上。
  - 免 ICP 备案(备案只针对大陆物理服务器);东京↔大陆延迟约 30–80ms,文字阅读产品可接受。
  - 天然保留海外推广空间:以后加一台海外机器即可,代码不改。
- **短信发送 = 可插拔接口**:`dev` 驱动(验证码打到日志/页面,开发不被阻塞)/ `aliyun` 驱动(真实)。

### 1.1 短信与备案(澄清,避免再混淆)

两件**不相干**的事:

1. **网站放东京服务器 → 不需要 ICP 备案。**
2. **发短信验证码 → 是阿里云「短信服务」API 调用,与服务器位置无关**,东京 ECS 照常能调。
3. 阿里云短信有**自己的一道"签名+模板"审核**(≠ 网站备案)。个人实名账号可选的签名来源里,「网站」要求该网站已 ICP 备案(与东京免备案冲突);但「**公众号/小程序名称**」「APP 名称」来源**不要求网站备案**。
   - **推荐绕法**:注册个人微信订阅号,用其名称作短信签名来源 → 个人也能过审,且与网站放东京不冲突。
   - 待办(用户侧,并行进行,不阻塞开发):办订阅号 + 阿里云短信签名/模板审核;拿到 AccessKey 后切 `aliyun` 驱动。

> 置信度:第 1–3 点大框架把握高;"个人签名审核各来源的具体材料要求"阿里云时有微调,申请时以当时控制台为准。

## 2. 数据模型

| 实体 | 关键字段 | 说明 |
|---|---|---|
| **User** | id, phone(唯一), display_name?, created_at | A 与 B 同表,靠是否拥有 Note/Card 区分角色 |
| **Note** | id, user_id(作者=A), body(text), created_at, updated_at | `created_at` = 录入时刻,**可见性时间判断用它** |
| **Tag** | id, user_id, name, unique(user_id, name) | 标签属于某个 A |
| **NoteTag** | note_id, tag_id, PK(note_id, tag_id) | 多对多 |
| **Card** | id, user_id(主人=A), title, visible_until, invite_code(唯一,归一化大写), created_at | `visible_until` 默认 = created_at |
| **CardTag** | card_id, tag_id, **is_auto_update**(默认 false), PK(card_id, tag_id) | 池子里的标签 + 每个是否自动更新 |
| **CardHolder** | id, card_id, user_id(读者 B), redeemed_at, unique(card_id, user_id) | B 输码后生成的绑定 |
| **PhoneOtp** | phone, code_hash, expires_at, attempts | 短信验证码临时表 |
| **RedeemAttempt** | (account/IP), ts, success | 邀请码兑换限流审计(可用计数器/缓存替代) |

会话:cookie-based session(长效 30–90 天),可用 Session 表或成熟 auth 库。

### 2.1 时间语义

- Note 的 `created_at` = **录入(粘贴/新建)时刻**,默认即可见性判断依据。
- 粘进来的旧日记默认拿"今天"的时间戳 → 一张 cutoff 在昨天的卡不会立刻显示它,除非 A 推进时间或该标签开了自动更新。**这是预期行为。**
- 内容"回填历史日期"(backdating)留作未来选项,MVP 不做。
- 编辑 Note 改 `updated_at`,**不改** `created_at`,故不影响已计算的可见范围。

## 3. 权限模型 —— 核心可见性规则(实现绝不能搞错)

读者 B 看卡 C 时,**服务端实时计算**可见 Note 集合 V:

> Note n 可见 ⟺ n 属于卡主 A,且**存在**某标签 T 同时满足:
> T 在卡 C 的池子 ∧ n 打了 T ∧(**T 开了自动更新** 或 **n.created_at ≤ C.visible_until**)

参考 SQL:

```sql
SELECT DISTINCT n.*
FROM notes n
JOIN note_tags nt ON nt.note_id = n.id
JOIN card_tags ct ON ct.tag_id = nt.tag_id AND ct.card_id = :cardId
WHERE n.user_id = :cardOwnerId
  AND (ct.is_auto_update = TRUE OR n.created_at <= :visibleUntil);
```

三种动态更新由这一条**自动满足**,无需额外逻辑:

- **推进时间** = `visible_until := now()`,更多旧内容落入范围。
- **增/减标签** = 改 CardTag 行;**移出后实时重算,相关 Note 自动消失、零痕迹**(§2.4 静默原则天然达成)。
- **自动更新** = 该 CardTag `is_auto_update=true`,新内容绕过时间判断直接可见。

### 3.1 两个 tab 的语义

- **「最近更新」tab**(B 进入卡的默认 tab)= V 按 `created_at` 倒序取最新 20 条。**是 V 之内的最新,绝不是 A 全库最新。**
- **标签 tab T** = **先全局算出 V,再按"含标签 T"过滤**(而非按 T 单独算可见性)。理由:一条 Note 只要已在 V 里,归到哪个 tab 都不构成新泄漏;此法最简单且绝不漏。排序 `created_at` 倒序(时间线样式留待以后)。

## 4. 防泄漏红线(实现必须遵守)

1. **给读者渲染 Note 时,只显示该 Note 标签中 ∩ 卡池子的那部分**(或干脆不显示标签)。否则泄漏 A 未开放的标签名(如一条打了「原生家庭」(开放)+「父亲」(未开放),不能让 B 看见"父亲")。
2. 所有可见性查询**一律服务端实时计算**;前端只拿结果,绝不下发 A 全量数据再前端过滤。
3. 读者侧**不写任何回传**(无已读/停留/进度),A 端也无此读取面。A 看不到 B 的任何阅读行为。
4. 任何"曾经可见、现在不可见"的内容,接口**不返回、不留痕**;B 只可能在主动回访时察觉内容变少。

## 5. 邀请码

- **形式**:4 位,数字 + 字母,**不区分大小写**(百度网盘风格);存储归一化为大写;字符集 [0-9A-Z](可选剔除易混淆 0/O/1/I/L,留作实现微调)。
- 一张卡一个码;可被多名受众输入兑换,每次兑换生成一条 CardHolder(unique(card_id, user_id) 防重复绑定)。
- **安全**:4 位不区分大小写 ≈ 36⁴ ≈ 168 万空间,是**单因子**(B 只输码,不像百度还要长链接)。故:
  - 兑换接口**严格限流**:同账号/同 IP 连续输错触发指数退避 + 锁定;全局异常枚举检测。
  - 码归一化大写 + 唯一约束 + 生成碰撞重试。
  - A 可作废/轮换码(实现项)。
  - 局限明示:若以后转公开/上规模,需加长码或改"链接+码"两因子。

## 6. 鉴权与会话

- **OTP 无密码**:注册与登录都用「手机号 + 短信验证码」,**不做密码**(省掉密码存储/找回)。
- **长效会话 Cookie(30–90 天)**:读者 OTP 一次即长期免登 → 短信量极低,不会每次访问都发。
- OTP 表存 code 的哈希、过期时间、尝试次数;发送/校验都限流。

## 7. 用户流程

### 7.1 写作端 A(MVP 主干)

1. 手机号注册/登录(OTP)。
2. 新建或粘贴 Note。
3. 给 Note 打一个或多个标签。
4. 浏览/搜索/筛选自己的库(按标签筛 + `ILIKE` 子串搜索;中文全文检索留待以后)。
5. 建卡:选若干标签入池 → 生成 4 位随机码/分享入口。
6. 维护卡:推进时间 / 增减标签 / 给标签开自动更新 / 作废码。
7. (Phase 2)AI 帮忙整理库、建议标签。

### 7.2 读者端 B

1. 手机号注册/登录(OTP)。
2. 若无任何卡 → 提示输入邀请码 → 载入对应卡。
3. 若已有 N 张卡 → 进入"邀请卡列表页";底部"添加新的邀请卡"按钮 → 悬浮框输码 → 载入新卡。
4. 单张卡详情页:顶部一行标签 tab,第一个固定为「最近更新」(默认),其余 = A 在此卡开放的标签。
5. 阅读页**零压力**:无点赞、无评论框、无已读回执、无"请回复"引导。

## 8. AI(Phase 2,brief §三)

- **只用在帮 A 整理库这一侧,不碰读者侧。**
- 功能:把新粘的零散 Note 聚类成主题/时间线,提示"这几条像在讲同一件事,要不要打同一个标签",降低维护成本。
- 用 **Claude API**(实现时读 `claude-api` 技能确认模型 id/用法)。
- **明确不做**:给读者的 AI 摘要、读者向 AI 提问、人格分析/诊断/匹配评分等任何"解读用户"功能。
- 单独接,不阻塞 Phase 1。

## 9. MVP 明确不做(brief §六)

读者侧 AI 摘要/问答;人格分析/诊断/关系匹配;给读者的通知/消息流/"卡有更新"提醒(全部默认静默);逐条审阅/发送前审核;公开卡免注册查看;社交广场/推荐/陌生人匹配/复杂多层级权限/增长裂变/会员;第三方平台自动同步导入。

## 10. 构建顺序

- **Phase 1(主干)**:A 注册→写 Note→打标签→建卡→出 4 位码;B 注册→输码→读(含 §3 权限计算 + §4 三条红线 + §5 限流)。短信用 `dev` 驱动。
- **Phase 2(AI)**:A 端库整理/标签建议,接 Claude API。
- **并行(用户侧 ops)**:订阅号 + 阿里云短信签名/模板审核 → 切 `aliyun` 驱动;买域名指向东京 ECS + HTTPS。

## 11. 仍开放/留待实现微调

- 邀请码字符集是否剔除易混淆字符。
- 标签 tab 内是否做时间线样式(MVP 先简单倒序列表)。
- 限流的具体阈值与存储(内存计数器 / Redis / 表)。
- 长效会话的具体时长与"记住此设备"。
